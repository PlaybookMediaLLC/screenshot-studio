# RFC Detail Audit

**Date:** 2026-08-26  
**Resolved:** 2026-08-26  
**Scope:** [RFC 001](001-guided-release-kit.md) through [RFC 033](033-workspace-migration.md)

## Purpose

This audit identifies which RFCs need additional product or implementation detail before engineering work can proceed safely. It evaluates whether each RFC defines its contracts, lifecycle, authorization, failure behavior, rollout, and testable completion criteria.

## Status

Every RFC identified below has been expanded. The audit is retained as the record of what was missing and as the checklist any future RFC is measured against. The tables now describe detail that the target documents contain rather than detail they lack.

Two gaps surfaced during expansion that no existing RFC owns. Both block the [RFC 021](021-core-workflows.md) chargeable milestone and still need documents written:

1. **Billing with usage quotas.** [RFC 034](034-rest-api-scalar-reference.md) defines the entitlement and quota enforcement mechanism. No RFC defines the plans, the metering of generation and rendering, or the customer-facing billing lifecycle.
2. **Authenticated page capture.** [RFC 013](013-product-asset-map.md) and [RFC 023](023-deployment-screenshot-automation.md) both stop at the same boundary. Most product screens worth marketing sit behind a login, and credential handling for a customer's own application needs its own security review.

A third item is scoped inside an existing RFC but is worth tracking separately: [RFC 020](020-postiz-publishing.md) records that self-service publishing depends on Postiz OAuth, which is not implemented. Until it is, channel connections require operator provisioning.

Expansion also surfaced one blocking dependency that was not previously recorded. Every approval decision, including `submit`, resolves through `requireActiveSessionOrganization` and so is session-only. No automated producer can move a draft to `READY_FOR_REVIEW`, which [RFC 029](029-recurring-campaign-generation.md) requires in order to function at all. [RFC 019](019-approval-workflow.md) carries the fix as a planned refinement: a separate machine-submission procedure, deliberately not a relaxation of `decideApproval`, so that `approve`, `reject`, and `request_changes` remain reachable only by a human.

## Recommended expansion order

The roadmap marks RFCs 019 and 020 as implemented. Their gaps were documentation backfill and have been reconciled against the shipped behavior rather than used to redesign it. For unimplemented work, detail precedes implementation.

The order that was followed, and that remains the implementation order:

## Standard sections

Short product RFCs use a shared expansion checklist. Every expanded document above follows it, and every new RFC should:

1. Goals and non-goals
2. User and system workflows
3. Typed data and API contracts
4. Lifecycle or state machine
5. Authorization and tenant isolation
6. Failure, retry, cancellation, and idempotency behavior
7. Security and privacy threats
8. Observability and cost limits
9. Rollout and migration plan
10. Testable acceptance criteria

## Recurring invariants

Expansion surfaced a small set of rules that recur across the platform. They are recorded here so a future RFC inherits them rather than re-deriving them:

- **Tenancy is resolved from the principal, never from input.** A supplied identifier selects an already authorized record; it never grants access. Unknown or foreign identifiers return `404`.
- **Machines create; humans approve.** Approval requires a session principal with a user identity. No tool, key, or service principal can approve, schedule, or publish.
- **Untrusted text never becomes an instruction or an action.** Crawled pages, PR bodies, and research results enter models as delimited data, with no tools attached and schema-constrained output.
- **Classification may restrict, never permit.** A model can add a restrictive tag and can never clear one set deterministically.
- **Every ambiguity fails toward review.** Timeouts, outages, unreadable records, and conflicting rules all resolve to requiring a human.
- **Approved content is immutable.** Content hashes pin what a human approved and are re-verified before scheduling and publishing.
- **Provider seams stay narrow.** Screenshot, scheduling, search, and deployment providers each implement one function behind an application-owned abstraction.
- **Generated artifacts carry provenance.** Model, prompt version, and input references are recorded so quality regressions are traceable.

## Purpose

This audit identifies which RFCs need additional product or implementation detail before engineering work can proceed safely. It evaluates whether each RFC defines its contracts, lifecycle, authorization, failure behavior, rollout, and testable completion criteria.

## Status

Every RFC identified below has been expanded. The audit is retained as the record of what was missing and as the checklist any future RFC is measured against. The tables now describe detail that the target documents contain rather than detail they lack.

Two gaps surfaced during the original expansion. Billing is now owned by [RFC 023](023-pricing-and-unit-economics.md), and authenticated capture by [RFC 007](007-authenticated-product-capture.md). The findings below record the historical audit:

1. **Billing with usage quotas.** [RFC 014](014-rest-api-scalar-reference.md) defines the entitlement and quota enforcement mechanism. No RFC defines the plans, the metering of generation and rendering, or the customer-facing billing lifecycle.
2. **Authenticated page capture.** [RFC 018](018-product-asset-map.md) and [RFC 029](029-deployment-screenshot-automation.md) both stop at the same boundary. Most product screens worth marketing sit behind a login, and credential handling for a customer's own application needs its own security review.

A third item is scoped inside an existing RFC but is worth tracking separately: [RFC 030](030-social-publishing.md) records that self-service publishing depends on social API OAuth, which is not implemented. Until it is, channel connections require operator provisioning.

Expansion also surfaced one blocking dependency that was not previously recorded. Every approval decision, including `submit`, resolves through `requireActiveSessionOrganization` and so is session-only. No automated producer can move a draft to `READY_FOR_REVIEW`, which [RFC 041](041-recurring-campaign-generation.md) requires in order to function at all. [RFC 012](012-approval-workflow.md) carries the fix as a planned refinement: a separate machine-submission procedure, deliberately not a relaxation of `decideApproval`, so that `approve`, `reject`, and `request_changes` remain reachable only by a human.

## Standard sections

Short product RFCs use a shared expansion checklist. Every expanded document above follows it, and every new RFC should:

1. Goals and non-goals
2. User and system workflows
3. Typed data and API contracts
4. Lifecycle or state machine
5. Authorization and tenant isolation
6. Failure, retry, cancellation, and idempotency behavior
7. Security and privacy threats
8. Observability and cost limits
9. Rollout and migration plan
10. Testable acceptance criteria

Working through this list revealed that applying it literally produces worse
documents than applying it thoughtfully, so two clarifications belong with it.

A section counts when the document answers the question, not when it carries
the heading. RFC 017 covers lifecycle through `Refresh`, RFC 018 through
`Freshness` and `Replacement semantics`, and RFC 048 bounds authority for all
three workflows in one `Cross-workflow contract` rather than repeating a threat
table three times. Renaming those to match the checklist would cost meaning and
add nothing. The reverse also holds: RFC 037 had an `Observability` heading over
a bullet list that never said which number would reveal failure, and that is a
gap despite the heading being present.

Items 7 and 8 are where documents most often fall short, because both are easy
to satisfy superficially. A threat table is worth writing only for features that
can actually do damage, and it should name what the feature does wrong rather
than list generic web risks. An observability section must elevate one metric
that would tell you the feature failed; a list of everything measurable is a
list of what is easy to instrument.

## Recurring invariants

Expansion surfaced a small set of rules that recur across the platform. They are recorded here so a future RFC inherits them rather than re-deriving them:

- **Tenancy is resolved from the principal, never from input.** A supplied identifier selects an already authorized record; it never grants access. Unknown or foreign identifiers return `404`.
- **`workspaceId` in a proposal means `organizationId` in the schema.** Later RFCs use "workspace" as the product-facing noun, but the persisted column is `organizationId`, the Better Auth organization ID defined by [RFC 010](010-planetscale-tenant-data-model.md), and `workspaceId` appears nowhere in `lib/`. Implementing any of these proposals means writing `organizationId`. The product vocabulary was kept because renaming it in the documents would misrepresent the UI, but the two names refer to one identifier and no migration is implied.
- **Machines create; humans approve.** Approval requires a session principal with a user identity. No tool, key, or service principal can approve, schedule, or publish.
- **Untrusted text never becomes an instruction or an action.** Crawled pages, PR bodies, and research results enter models as delimited data, with no tools attached and schema-constrained output.
- **Classification may restrict, never permit.** A model can add a restrictive tag and can never clear one set deterministically.
- **Every ambiguity fails toward review.** Timeouts, outages, unreadable records, and conflicting rules all resolve to requiring a human.
- **Approved content is immutable.** Content hashes pin what a human approved and are re-verified before scheduling and publishing.
- **Provider seams stay narrow.** Screenshot, scheduling, search, and deployment providers each implement one function behind an application-owned abstraction.
- **Generated artifacts carry provenance.** Model, prompt version, and input references are recorded so quality regressions are traceable.

## Verifying an RFC

`scripts/verify-rfcs.py` checks these documents against the code they describe.
It runs eighteen checks, covering document structure, historical audit coverage,
source-backed claims, active dependency order, script availability, canonical
priority numbering and the accuracy of this check count. The catalog check
requires every numbered RFC to appear once in priority order with a matching
filename/title, category and legacy mapping. Historical dependencies are
validated as references but do not impose a new implementation sequence.

Two of those checks were originally scoped to the RFCs marked Implemented and
were later widened to every document, because a claim about real code deserves
the same scrutiny wherever it appears. Citing a concrete source file is such a
claim, so every symbol named beside one must exist. Proposed schema fields in
`ts` blocks are exempt: they describe work to be done, not code that is there.

```
npm run verify:rfcs                    # runs inside npm run quality:check in CI
python3 scripts/verify-rfcs.py --self-test
```

The code-grounded checks matter more. Structural checks confirm a document is
well formed, which says nothing about whether it is true. Checking claims
against source is what found the errors that mattered during this expansion: a
transition table row that disagreed with `campaignPostTransitions`, a permission
identifier that existed nowhere, and an agent flow calling a function that was
never written. The promise check found two topics this audit asked for and the
documents did not deliver: cancellation semantics in RFC 041 and provider
reconciliation in RFC 039.

`--self-test` feeds deliberately broken input to every check and confirms each
one rejects it. A check that cannot fail proves nothing, so a passing suite is
only meaningful when the self-test passes too. Add the self-test case alongside
any new check.
